YOUR WORKSTREAM: the online foundation, host-agnostic. Today two humans can only play hot-seat or in two tabs of one browser over BroadcastChannel (src/net/broadcast.ts implements the two-method Transport in src/net/transport.ts; src/net/lockstep.ts is deterministic lockstep with input delay and desync hashes; src/net/room.ts is the join/start/ready handshake). Read docs/ROADMAP.md Phase 3 and the "Multiplayer spike" section first. The game itself deploys as static files to Vercel, which cannot hold WebSockets, so the relay must run as its own small service; the owner has not picked a host yet and is away, so build and test everything locally and make it deployable anywhere.

Build:
1. server/relay-core.ts: a pure, transport-free relay state machine (rooms keyed by code, max two peers, forwards envelopes between them, never inspects inputs beyond size/shape checks). Protections: message size cap, per-socket rate limit, room TTL and idle expiry, max rooms, heartbeat/ping timeouts, a clean "peer-left" notice to the survivor, reconnect into the same seat within a grace window using a per-seat token. Unit-test it thoroughly in bun (tests/relay.test.ts) with fake sockets and a fake clock.
2. server/bun.ts: a Bun.serve WebSocket adapter around the core (also serves GET /health), configured by env (PORT, ALLOWED_ORIGINS for an Origin allow-list, limits). A Dockerfile (oven/bun base) and short deploy notes for Fly.io / Render / Railway / any VPS in docs/ONLINE.md. Optionally a Cloudflare Durable Object adapter if you can keep it tiny and typed without new dependencies; mark it untested if you cannot run it.
3. src/net/websocket.ts: a Transport over WebSocket that talks to the relay, with automatic reconnect (exponential backoff, resumes the seat with its token) and a status signal (connecting / open / reconnecting / closed). Lockstep must survive a short drop because it already re-sends unacknowledged inputs.
4. Disconnect handling in lockstep/UI (roadmap exit criterion): when the peer goes silent, pause with a visible "Opponent disconnected, waiting 20 s" countdown, resume if they come back, otherwise end the match cleanly as an abandoned friendly (no rewards either way, nothing farmable).
5. Client flow: in the vs Player card (src/client/versus.ts), an "Online friendly" option shown only when a relay URL is configured: build-time constant from env DERBY_RELAY_URL in scripts/build.ts (empty by default, so production shows nothing until the owner deploys a relay), overridable for testing by ?relay=wss://... in the page URL. Host creates a room and gets a shareable invite link (https://derby.natwong.dev/?join=CODE, using location.origin) plus the code; opening the link or typing the code joins. Clear states for waiting, connecting, opponent left, version mismatch (send the sim/replay version in join and refuse mismatches with a friendly message).
6. server/verify.ts: re-simulate a replay code (src/meta/replay.ts) headlessly and return the final score, stats and fingerprint, so a future server can reject tampered results (Phase 2 exit criterion). Test that a tampered log is detected.
7. Tests: unit tests for every piece; an e2e test (tests/e2e/online.e2e.cjs, wired into tests/e2e/run.cjs) that starts the Bun relay on a free local port, opens two pages with ?relay=ws://127.0.0.1:<port>, pairs them, plays a few seconds of lockstep, checks both sides report the same state hash, kills one page and sees the disconnect countdown on the other. CI must run it (Bun is available in CI; check .github/workflows/ci.yml).
8. docs/ONLINE.md: architecture, protocol, limits, threat model (what a malicious client can and cannot do in lockstep: it can send any input for its own team, it cannot change the other side; results of online friendlies are not trusted for Elo until a server re-simulates), how to run locally, how to deploy, and exactly what the owner must decide or provide to go live (a host account, a domain such as relay.derby.natwong.dev, setting DERBY_RELAY_URL in Vercel).
